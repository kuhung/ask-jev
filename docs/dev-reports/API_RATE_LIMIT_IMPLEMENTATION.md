## 任务优先级与交付清单

### P0：核心防刷与安全阻断（必须交付）
- **双层滑动窗口限制**：
  - 突发限流：单 IP 在 5 秒内最多允许 5 次提问请求，防止暴力点击与并发攻击；
  - 持续限流：单 IP 在 60 秒内最多允许 20 次提问请求，防止长期慢速爬取与配额消耗。
- **前置短路拦截**：在 `app/api/jev/route.ts` 最前置阶段完成频控校验，命中拦截立即返回 HTTP 429 与标准响应头（`Retry-After`、`X-RateLimit-*`），停止后续 JSON 解析与远程请求。

### P1：客户端交互全入口闭环（高优先级）
- **异常精确感知**：在 `app/page.tsx` 中区分 429 状态码，弹出「老管家正忙：提问太频繁啦，请稍候 X 秒再试！」Toast 提示，停止加载态；
- **全入口覆盖**：覆盖自由输入提问（`handleAsk`）与场景词条快捷点击（`handleSelectTopic`）两条用户真实交互链路。

### P2：系统稳健性与自动化防护（长效保障）
- **防内存泄漏修剪机制**：维护最大 10,000 个活跃 IP 缓存上限，每分钟主动淘汰过期记录，超限时使用 FIFO 淘汰最旧记录，常驻内存稳定在数兆字节以内；
- **自动化集成测试**：编写 `scripts/test-rate-limit.mjs`，覆盖 IP 提取、突发拦截、租户隔离、持续上限、内存修剪 5 大测试用例。

## 方案消融分析 (Ablation Verification)

为避免冗余代码与过度设计，对本次改动执行方案消融自检：

1. **能否移除持续周期窗口（只保留突发窗口）？**
   - 若仅保留 5 秒 5 次限制，攻击者可以通过每秒发送 1 次请求在 1 小时内消耗 3600 次后端资源。双层窗口具备必要性。
2. **能否移除内存容量修剪机制？**
   - 在长时间运行和多客户端访问的生产环境下，只增不减的 Map 会导致内存持续线性膨胀。定时修剪与容量上限是常驻进程的必要防线。
3. **前端能否直接回退到 Mock 数据而不弹出提示？**
   - 生产环境中若将 429 静默降级为 Mock，用户无法得知已被频控拦截，且误以为接口持续正常响应。显式提示有利于引导用户合理调整提问节奏。
